# Архитектура Freeplay Extras: разбор и план (2026-11-28)

Основание: чтение кода и конфигов, на игре не проверялось. Всё, что про поведение движка, помечено как допущение.

## 1. Как устроено сейчас

Слои сверху вниз:

1. **Ядро SRP** (папка `gamedata` репозитория) не правится. Аддон переопределяет файлы копиями (28 файлов, ниже).
2. **Базовый слой:** `fp_binder` (подкласс биндера актора, `actor.ltx` меняет одну строку), `ogse_signals` (шина сигналов и слотов), `ogse_signals_addons_list` (список модулей), `fp_log` (лог с выключателями в `misc\fp_log.ltx`).
3. **Модули** (`fp_*`, `ogsm_*`): каждый имеет `attach(mgr)`, подписывается на сигналы, читает свой `misc\fp_<имя>.ltx`, включается через `has_alife_info` (общий флаг `srp_freeplay` или свой info).
4. **Инструменты разработчика:** `fp_dev`, `fp_dev_tools`, `ui_cheat_*`, `collect_sections`.

Что сделано хорошо и менять не надо:
- ядро не правится, только подкласс биндера и копии конфигов;
- вся жизнь модулей идёт через одну шину, обработчики имеют `script_name`, медленные видно в логе;
- у каждого модуля свой конфиг и свой выключатель;
- pstor не используется (по замеру 4 байта из 6144).

## 2. Риски, по убыванию важности

### R1. Формат сохранения без границ (главный риск)
Модули пишут в пакет актора подряд, без метки и длины (`on_save`/`on_load` у `fp_satiety`, `fp_mutants`, `fp_quests`, `ogsm_rare_items_manager`, `ogsm_rt_manager`, `fp_fatigue`). Порядок записи задаёт список в `ogse_signals_addons_list`. Из этого следует:
- новый модуль в середине списка, удаление модуля или смена порядка ломает чтение всех сохранений: данные одного модуля читает другой;
- защита от «данных нет» есть только у `fp_fatigue` (`r_elapsed() >= 5`), поэтому он стоит последним «вручную»;
- ошибка в `on_load` одного модуля сдвигает чтение всех следующих.
Это то, что превратит любое наращивание в «трагедию».

Предложение: контейнер с рамкой. Начало блока: метка `FPSTATE`, версия формата. Дальше для каждого модуля: имя, версия модуля, длина данных, данные. При загрузке: известный модуль читает свой кусок и получает версию, неизвестный пропускается по длине (`reader:r_advance`), отсутствующий получает пустое состояние. Старые сохранения (без метки) читаются прежним путём. Допущение: `net_packet:w_chunk_open16/close16` и `reader:r_tell/r_advance` есть в API (по `lua_help.script`, в игре не проверял). Цена: около 100 строк в `fp_binder` и небольшая правка 6 модулей (`on_load(reader, version)`), одно изменение формата, после которого порядок и состав модулей больше не важны.

### R2. Копия `system.ltx`
Копия содержит 40 отличающихся строк. При обновлении SRP её нужно сливать вручную. Ядро уже включает `external.ltx` («add your custom files here») после всех файлов предметов, так что девять `#include` аддона (`fp_*_items`, `fp_outfit`, `fp_artefacts`, `fp_dev` и т. д.) можно перенести туда: копия `external.ltx` меняется редко. В `system.ltx` останутся только правки, которые include не заменяет: список диалогов, `npc_profile_fp`, `script_binding` аномалии, секция `[document]`. Допущение: порядок наследования секций (`:parent`) выдерживается, так как `external.ltx` идёт после `outfit.ltx`, `artefacts.ltx`, `devices.ltx`. Проверить в игре.

### R3. Дрейф копий ядра
Копий 28 (см. таблицу ниже). Если SRP обновится, расхождение никто не заметит. Предложение: `tools/check_core_drift.py` и файл `docs/core_copies.md` с хэшем базы, с которой снята копия; скрипт сравнивает копию с текущим файлом ядра и печатает, что изменилось в ядре с момента копии.

### R4. Полные проходы по 65 тысячам id
Остались 4 места: `fp_sleep.recreate_mattresses`, `fp_dev_tools` (строка 332), `ogsm_bring_items.ensure_loot` (разовая миграция) и `flash_holders` (инструмент). Все вызываются редко. Если нужны будут новые, делать общий помощник `fp_world.scan(fn, budget_ms)`, который режет проход на кусочки по времени, как делает уборщик.

### R5. Выключатели модулей
12 одинаковых `is_enabled` в двух вариантах (с `_off` и без). Любой новый модуль копирует одну из них. Предложение: `fp_core.enabled("имя")` с единым правилом «`srp_freeplay` или `fp_<имя>`, и не `fp_<имя>_off`». Риск низкий, польза в единообразии.

### R6. Инструменты разработчика в основном аддоне
`fp_dev`, `fp_dev_tools` (33 КБ, пять разных задач в одном файле: прыжки, телепорт, время, логи, диагностика), `ui_cheat_*`, `collect_sections` грузятся у каждого игрока. Предложение: отдельный аддон `freeplay_dev`, список модулей которого подключается к шине так же, как основной. Допущение: нужно проверить, что `signals_mgr` умеет принимать второй список. Заодно `fp_dev_tools` режется на `fp_dev_tools` (реестр и меню), `fp_dev_teleport`, `fp_dev_log`.

### R7. Локализация
В русском файле 453 строки, в остальных восьми языках по 34 (одинаковые заглушки, 4454 байта). Если язык игры не русский, большая часть текстов покажется как id. Для русскоязычной сборки не критично. Вариант: оставить только `rus` и `eng` (английский с переводом ключевых строк), остальные не держать.

### R8. Порядок и мусор
- `README.md` 58 КБ и местами устарел (в нём список модулей `fp_surge, fp_dev`, а в списке их 19). Предложение: README оставить входом (установка, список модулей и их info), подробности по модулям вынести в `docs/`.
- В корне аддона лежат два лишних `new_items_icons.txt`.
- `ogsm_packet` (разбор пакетов для создания предметов) используется только `ogsm_rt_manager` и `ogsm_bring_items`: оставить.

## 3. План по приоритету

1. **R1** контейнер сохранения с рамкой (самое важное для надёжности, меняет формат один раз).
2. **R2** перенос include в `external.ltx` (меньше ручной работы при обновлении SRP).
3. **R3** скрипт сверки копий с ядром.
4. **R5** единый выключатель, затем **R6** разделение dev-инструментов.
5. **R4**, **R7**, **R8** по необходимости.

Порядок можно менять. R1 и R2 затрагивают сохранения и загрузку конфигов, поэтому делать их стоит по одному, каждый раз с проверкой в игре на новом и на старом сохранении.

## 4. Хранилище (fp_store), реализовано в b21

Все модули, у которых есть состояние в сохранении, регистрируют кадр через `fp_store.register{ name, version, save, load, legacy }`. Формат: `u32 FPST`, `u8 формат`, `u8 число кадров`, затем на каждый модуль имя, версия, длина (u16), данные.

Правила для новых модулей (по порядку выбора):
1. **Флаг (да/нет)** это info portion (`fp_store.set_flag/get_flag`). id надо объявить в `info_portions.xml`. В пакет актора такие данные не попадают.
2. **Состояние модуля** (счётчики, списки, таймеры) это кадр `fp_store.register`. Пишите компактно: имена из конфигов как `fp_store.h16(имя)` (2 байта), id как u16/u32, без строк, которые можно восстановить из конфига. При смене формата поднимайте `version` и оставляйте чтение старой версии в `load(reader, version)`.
3. **pstor** только для значений, которые должны читать условия ядра (`xr_logic`, ltx): `fp_store.pstor_set/pstor_get`.

Что даёт кадр: модуль находится по имени, поэтому добавление, удаление и перестановка модулей не ломают сохранения; ошибка чтения одного модуля не портит чтение следующих (после модуля читатель всегда переводится на конец его кадра); кадр удалённого модуля пропускается по длине. Сохранения старого формата (без метки) читаются по-старому: порядок шести прежних модулей зафиксирован, переставлять их в `ogse_signals_addons_list` нельзя.

Учёт: на каждом сохранении в лог идёт строка `[fp_store] SAVE N frames, M bytes: имя=размер ...`, а `[fp_binder] SAVE actor chunk` показывает весь блок актора. Предел блока по ядру SRP: `_g.set_save_marker` прерывает сохранение на 10240 байт для проверяемых пакетов, на 16000 для самого пакета; моя оценка 6 КБ из IX-Ray консервативнее.

Упаковка в b21: `fp_mutants` (секции хэшем h16, id отряда u32) и `ogsm_rare_items_manager` (имена торговцев и предметов хэшем h16). Остальные формат не меняли (они маленькие).

## 5. Задания: фасад fp_tasks (b27)

Раньше выдачей, новостями и обновлением заданий занимались три места: `fp_quests`, `ogsm_rt_manager` и родной менеджер. Теперь модули Freeplay разговаривают с движком о заданиях через один модуль `fp_tasks` (около 100 строк):

- `give{...}` создаёт задание движка (`CGameTask`): название, описание, метка на карте, функции завершения и провала в виде имени `"модуль.функция"`, ограничение по времени, новость "новое";
- `update(id, {...})` меняет название, описание и цель уже выданного задания;
- `finish(id, ok, текст)` ставит состояние "выполнено/провалено" и шлёт новость;
- `news(kind, text, icon)` - единственная реализация новостей (строка новостей + сообщение в окне разговора, 4 аргумента `give_talk_message2`);
- `state(id)` - состояние задания.

Правила:
- У `fp_tasks` нет собственного состояния и записи в сохранение: задание и имена его функций проверки хранит движок, мировое состояние (спавн, волны, цели) хранит модуль-заказчик.
- Родной менеджер (`task_manager.script`) не копируется и не используется: его задания остаются родными. Если нужны счётчики или репутация родного менеджера, они вызываются явно (`xr_statistic.inc_*`).
- Данные заданий остаются в конфигах модулей (`fp_quests.ltx`, `rt_manager.ltx`); общий формат данных пока не вводится. Если понадобится ещё один модуль заданий, он просто вызывает `fp_tasks`.
- Пилот b26 (этапы, свой разбор условий, конвертер SoC `tasks.xml`) удалён; он остаётся в истории git (коммит d30dc07), если перенос заданий "Тени Чернобыля" понадобится.

Сигналы и задания: `fp_tasks` сам на сигналы не подписан, модули вызывают его напрямую. Реакцию на завершение и провал заданий модули получают из сигнала `on_task` (его испускает `fp_binder` для заданий не из родного менеджера; `ogsm_rt_manager` на него подписан через `fp_on_task`).

Отложено (сделать, когда появится первое задание, которое должно меняться само по ходу мира, например сводка погоды или выброс): метод `fp_tasks.watch(id, { title = fn, text = fn, target = fn })` по идее функторов Зова Припяти (`task_functor`). Он хранит функторы в памяти, раз в 500-700 мс пересчитывает их и при изменении вызывает `update` с новостью. После загрузки сохранения таблица пуста, поэтому модуль-заказчик заново регистрирует функторы для своих активных заданий. Цена: у `fp_tasks` появится состояние в памяти и проверка по таймеру.
